# ПАСПОРТ ПРОЕКТА
## Экологический проект «Чистый берег» — цифровой продукт «Clear Shore»

---

## 1. Анализ исходной ситуации, целевых аудиторий и аналогов

### 1.1 Исходная ситуация
Проект «Чистый берег» (Фонд защитников природы, «СР Дата», при поддержке Яндекс.Облака) объединяет обучение, мониторинг и уборку побережий с использованием ДЗЗ и аэрофотосъёмки. Команда разрабатывает цифровой продукт **Clear Shore** — приложение, которое привлекает аудиторию к экологии через поиск и фиксацию загрязнений с помощью ИИ-анализа фотографий, а также организацию офлайн-уборок.

### 1.2 Целевые аудитории
- **Молодёжь от 14 лет**, интересующаяся экологией и технологиями — мотивирована интересом к ИИ/геймификации, желанием реального вклада, соцдоказательством.
- **Сотрудники ООПТ** — мотивированы должностной необходимостью мониторинга территории; ключевой барьер — доверие к точности ИИ-детекции.

Специализированный кабинет и отдельные сценарии для ООПТ на данном этапе не входят в MVP и вынесены в отдельный документ «План развития».

### 1.3 Аналоги
Прямого анализа конкурентов команда на старте не проводила, поэтому ниже — краткий обзор существующих решений в смежной нише «гражданская наука + загрязнение окружающей среды», чтобы обозначить контекст рынка:

- **Litterati** — мобильное приложение, в котором пользователи фотографируют мусор, а ИИ распознаёт тип и материал предмета; данные собираются в открытую базу и карту загрязнений.
- **Marine Debris Tracker** и **OpenLitterMap** — открытые платформы гражданской науки для картирования мусора и пластикового загрязнения по фотографиям с геометками.
- **Planet Patrol** — приложение для логирования находок мусора с фото на интерактивной карте, ориентированное на волонтёров.
- **River Watchers** (River Cleanup + VITO) — проект, где по фотографиям от жителей ИИ определяет тип отходов и формирует карту загрязнения рек.

**Вывод:** большинство аналогов решают только задачу сбора и картирования данных о загрязнении, но не строят единый путь «привлечение → обучение → мониторинг → офлайн-уборка → удержание» для двух разных аудиторий одновременно. Это отличие — основа ценностного предложения Clear Shore.

## 2. Цель проекта, ценностное предложение, пользовательские пути

### 2.1 Цель
Привлечь аудиторию к экологии через приложение Clear Shore, которое с помощью ДЗЗ и пользовательской фотофиксации выявляет загрязнённые зоны побережий, и довести пользователя от разового интереса до регулярного участия — как в цифровом мониторинге, так и в реальных уборках.

### 2.2 Ценностное предложение
Пользователь получает простой инструмент, который с помощью ИИ мгновенно определяет степень загрязнения по фото и сразу показывает находку на карте; а также может довести дело до конца — записаться на уборку этой же зоны и увидеть результат «было/стало».

### 2.3 Пользовательский путь (MVP)
1. Скачивание приложения.
2. Регистрация/вход (кнопка регистрации ведёт на сайт).
3. По умолчанию открывается вкладка «Карта» (на основе Яндекс.Карт).
4. Переход во вкладку «Задания» — два варианта:
   - «Поиск загрязнённых мест» — съёмка через встроенную камеру, автофиксация координат и времени, отправка фото в Vision-модель, определение степени загрязнения, метка сразу отображается на карте.
   - «Участие в уборке» — пользователь видит на карте зоны, требующие уборки, записывается на офлайн-мероприятие или самостоятельную уборку найденной точки, по завершении фотографирует результат.
5. Повторное взаимодействие — новые находки, участие в новых уборках, общение с ИИ-ассистентом.

## 3. Стратегия привлечения, обучения, вовлечения и удержания

- **Привлечение:** информация о проекте через сайт (лендинг с картой и историей проекта), соцсети, партнёрство с Фондом защитников природы и офлайн-акции на побережьях.
- **Обучение:** на первом этапе — короткая онбординг-инструкция в приложении (как искать загрязнения, как пользоваться камерой и картой); полноценный образовательный модуль — направление для развития (см. «План развития»).
- **Вовлечение:** два типа заданий («поиск» и «уборка») формируют естественный цикл — найти проблему → решить проблему → увидеть результат на карте.
- **Удержание:** визуальный вклад пользователя на карте, возможность увидеть изменение статуса точки после уборки, диалог с ИИ-ассистентом как постоянная точка взаимодействия с приложением.

## 4. Мероприятия и другие механики проекта
- Задание «Участие в уборке» как встроенная в приложение механика перехода от цифрового мониторинга к офлайн-действию.
- Отображение истории «было/стало» по каждой точке — фото до и после уборки.
- ИИ-чат-ассистент как постоянная механика вовлечения: отвечает на вопросы по экологии и даёт советы непосредственно во время уборки загрязнённых мест (например, как правильно сортировать/утилизировать найденный мусор).

## 5. Концепция цифрового продукта, ключевые функции и пользовательские сценарии

### 5.1 Формат
Экосистема Clear Shore: мобильное приложение (Flutter, Android/iOS) + веб-сайт (React) на едином backend (Python) и общей базе данных.

### 5.2 Ключевые функции
1. **Карта** — отображение всех зафиксированных точек загрязнения (на базе Яндекс.Карт).
2. **Задание «Поиск загрязнённых мест»** — камера → фото + гео + время → Vision-модель → степень загрязнения → метка сразу видна на карте (без модерации на этапе MVP).
3. **Задание «Участие в уборке»** — просмотр зон для уборки, запись, подтверждение результата фотографией.
4. **ИИ-чат-ассистент** — отвечает на вопросы по экологии и даёт советы по уборке найденных загрязнений.
5. **Сайт** — публичный лендинг, регистрация, публичная карта.

### 5.3 Пользовательский сценарий
Пользователь находит замусоренный участок побережья → открывает приложение → «Задания» → «Поиск загрязнённых мест» → фотографирует → получает от ИИ оценку степени загрязнения → метка появляется на карте → пользователь (тот же или другой) открывает задание «Участие в уборке» на этой точке → убирает территорию → фотографирует результат → статус точки меняется → при затруднениях в процессе уборки пользователь может спросить совета у ИИ-чата.

## 6. Прототип, техническая архитектура, данные, технологии и интеграции

### 6.1 Технологический стек
- **IDE:** Visual Studio Code
- **Веб-сайт:** React
- **Мобильное приложение:** Flutter (Android/iOS)
- **Backend:** Python (единый REST API сервер)
- **Нейросети:** OpenRouter — модель с Vision (детекция загрязнения по фото) и отдельная модель для чата (советы по экологии и уборке)
- **База данных:** PostgreSQL + расширение PostGIS
- **Карта:** Яндекс.Карты

### 6.2 Архитектурная схема
```
[ Мобилка (Flutter) ]   \
                         ===> [ REST API (Бэкенд: Python) ] ===> [ PostgreSQL / PostGIS ]
[ Веб-сайт (React)  ]   /                 ||
                                          || (Снимки ДЗЗ / Фото)
                                          \/
                                 [ OpenRouter API ] (Vision ML)
```
Отдельно чат-ассистент обращается к своей модели OpenRouter через тот же backend.

### 6.3 Потоки данных
1. Пользователь фотографирует находку → клиент прикрепляет геометку и время → отправка на backend.
2. Backend сохраняет фото и метаданные, отправляет изображение в Vision-модель OpenRouter.
3. Ответ модели (степень загрязнения) сохраняется в PostGIS и сразу отображается как точка на карте.
4. Задание «Участие в уборке» обновляет статус точки после подтверждения фото «после».
5. Запросы к чат-ассистенту обрабатываются backend'ом и передаются в отдельную LLM-модель OpenRouter.

### 6.4 Структура репозитория
```
├── /Clean-shore/   # Приложение (apk/ips), Flutter
├── /Site/          # Лендинговый сайт, React
└── /Backend/       # Единый сервер: API, БД, интеграция с ИИ (Python)
```

### 6.5 Прототип
Кликабельный прототип/MVP демонстрирует: онбординг → карта → задание «поиск загрязнения» → результат детекции → задание «участие в уборке» → фото результата → диалог с чат-ассистентом.

## 7. KPI и способ их измерения
Команда не определяла целевые числовые показатели заранее — ниже предложены метрики для оценки эффективности проекта после запуска:

| KPI | Что измеряет | Как собирается |
|---|---|---|
| Кол-во регистраций / месяц | Приток новой аудитории | Данные аккаунтов в БД |
| Кол-во зафиксированных точек загрязнения | Активность мониторинга | Кол-во меток в PostGIS |
| % точек, переведённых в статус «убрано» | Реальный экологический эффект | Соотношение меток «найдено» / «убрано» |
| Retention 30 дней | Удержание пользователей | Повторные входы/действия в приложении |
| Кол-во обращений к чат-ассистенту на пользователя | Вовлечённость в диалоговую механику | Логи запросов к чату |

*Фактическое достижение этих KPI не оценивалось в рамках хакатона — предложена только логика и способ измерения.*

## 8. План реализации, роли, ресурсы и основные статьи затрат

### 8.1 Команда (5 человек)
| Роль | Зона ответственности |
|---|---|
| 2 человека | Разработка приложения (Flutter, интеграция камеры, карты, чата) |
| 1 человек | Разработка сайта (React, лендинг, регистрация) |
| 1 человек | Оформление паспорта проекта, плана и презентации |
| 1 человек | Поддержание позитивной атмосферы в команде |

### 8.2 Основные статьи затрат (на этапе пилота)
- Облачный хостинг backend и базы данных.
- Оплата запросов к OpenRouter (Vision-модель + чат-модель) — переменная статья, зависит от числа пользователей и фото.
- Хранение фотографий (объектное хранилище).
- Использование API Яндекс.Карт.
Детальная финансовая модель на этапе хакатона не рассчитывалась.

### 8.3 Ресурсы
- Backend, база данных PostgreSQL/PostGIS, доступ к API OpenRouter и Яндекс.Карт — минимально необходимая инфраструктура для запуска MVP.
- Партнёрская поддержка Фонда защитников природы для организации офлайн-уборок по заданию «Участие в уборке».

## 9. Ключевые допущения, ограничения и риски

| Риск/ограничение | Способ снижения |
|---|---|
| Точность Vision-модели в определении степени загрязнения ограничена | Отображение результата как оценки ИИ, а не абсолютного факта; в будущем — возможность ручной коррекции |
| Доверие сотрудников ООПТ к ИИ-детекции низкое | Постепенное вовлечение ООПТ через демонстрацию точности на реальных пилотных точках, отдельный кабинет — в плане развития |
| MVP не включает модерацию меток | На старте принято решение показывать метки сразу — риск единичных некорректных меток на карте, компенсируется низкой критичностью MVP-этапа |
| Второй сценарий («уборка») зависит от офлайн-координации | Использование партнёрства с Фондом защитников природы для организации реальных мероприятий |

## 10. Ожидаемый результат и эффект от реализации проекта
- Работающий цикл «нашёл загрязнение → зафиксировал через ИИ → убрал → увидел результат на карте», объединяющий цифровой продукт с реальным экологическим эффектом.
- Рост вовлечённости молодёжной аудитории за счёт простого и быстрого сценария участия (два понятных задания).
- Формируемая база данных о загрязнённых точках побережий, полезная для дальнейшего анализа и, в перспективе, для сотрудников ООПТ.
- Постоянная точка взаимодействия с пользователем через ИИ-чат-ассистента, повышающая вовлечённость без необходимости отдельного обучающего модуля на старте.
